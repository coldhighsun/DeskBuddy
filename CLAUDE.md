# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

DeskBuddy is a Windows desktop pet (WPF, .NET 11, buildable on Windows only). Versions are generated by MinVer from git tags (`v1.2.3`).

## Design Requirement: Pet Extensibility (MUST follow)

Pets will keep being added, so every change must keep adding a pet a pure content task. Treat the following as hard rules, and check them before finishing any change:

1. **Adding a pet means dropping files into `pets/<name>/`** (`atlas.png` + `manifest.json`, optionally `icon.png`). It must never require a code change, a rebuild of any project, a registration list, a resx entry or a settings migration.
2. **Never hard-code a specific pet** anywhere in code, XAML, resources, tests or scripts: no pet names, sizes, frame counts, frame rates, facing directions, state lists, colors or file names. Everything comes from the pet's manifest and the `Pet` model. The only allowed name is the default pet (`PetSettings.DefaultPetName`, currently `robot`) used as the fallback.
3. **Never assume a pet defines a state.** Every state beyond `Idle` is optional. Missing states resolve through `Domain/Pets/PetStateFallback`; optional states (`Hop`, and anything added in the future) must be skipped entirely when the pet does not define them. Code must also cope with a state that has zero frames, a single frame, or a different `fps`.
4. **Never assume sizes or layouts.** Frame size, atlas size, cell size, column count and aspect ratio are per-pet. Window size, hit-testing, anchoring to the taskbar/screen edge, the umbrella/bubble offsets and the tray icon must derive from the pet's own `frameSize` and the user's scale setting.
5. **UI that depends on pet capabilities must be data-driven**: pet cards, capability tags, state previews, tray entries and the pet list are all derived from the manifest (`PetCapabilities`, `PetShowcase`, `FolderPetCatalog`), never from a hard-coded list of states or pets. A new pet must show up correctly without touching the panel.
6. **Loading must be tolerant and diagnosable**: an invalid or half-written pet (bad manifest, missing atlas, wrong cell size, out-of-range frame index) must be rejected with a clear log message and a user-facing reason via `ErrorText.For`, must never crash the app or hide the other pets, and the app falls back to the default pet. Never trust manifest values: validate them in `FolderPetLoader`.
7. **Extending the format is backward compatible**: new manifest fields and new `PetState` values must be optional, have a sensible default or fallback, and must not break pets that predate them (including pets users put in `%LOCALAPPDATA%\DeskBuddy\pets`). Whenever the manifest format or the set of states changes, update this file, the shipped pets and generation scripts, and `ShippedPetsTests` together.
8. **Prove extensibility with tests**: tests that need a pet build one on the fly (in memory or in a temp directory) with unusual shapes (different frame size, missing states, one-frame states, extra unknown states) instead of relying on a shipped pet's specifics. Do not write a test that would break when a new pet is added to `pets/` or an existing pet is redrawn.
9. **Pet creation stays cheap**: the generation scripts (`tools/Generate*Pet.ps1`, `PetVectorDrawing.ps1`, `PetVectorAnimations.ps1`, `PetVectorScenarios.ps1`, `PackPetAtlas.ps1`) hold the shared pipeline; a new shipped pet should only need a new script that draws poses. If you see duplicated logic across scripts, move it into the shared files instead of copying it again.
10. **Before adding any pet-related feature, ask:** "does this still work for a pet I have never seen?" If the answer is no, redesign it so it does.

- **The unit test count is hard-coded in the README badge** (`unit%20tests-N` and the `Unit tests: N` alt text, in both `README.md` and `README.zh-CN.md`; N is the sum over all four test projects, as reported by `dotnet test DeskBuddy.slnx`). Whenever a change adds, removes or parameterizes tests so the total changes, update the number in both READMEs in the same change.

The images and pets it uses are built inside the tests or placed in temp directories.

## Architecture

Four layers; dependencies point App → Application → Domain, and Infrastructure implements the interfaces defined by Application:

- **Domain**: pure logic with no infrastructure dependency. The pet behavior state machine (`Behavior/PetBehaviorStateMachine`), movement strategies (`Movement/`: walking along the taskbar, free fall, crawling along screen edges, hopping, with the screen abstracted by `IScreenEdges`), scenario selection (`Scenarios/`), the pet model (`Pets/`), settings (`Settings/PetSettings`), the sit-too-long reminder, etc. All pet states are the `PetState` enum.
- **Application**: use cases and services. `PetBrain` combines sensor input and user interaction and is the single entry point for the UI to ask "what should the pet do now?". Grouped by folder: `Settings/` (`SettingsService`, `SettingsApplier`), `Scenarios/` (`DevScenarios`, `SystemScenarios`), `Sensors/` (cached/throttled sensor wrappers), `Hotkeys/` (`BossKeyController`); `Abstractions/` defines the sensor and storage interfaces (`ISettingsStore`, `IPetLoader`, etc.).
- **Infrastructure**: Windows implementations of those interfaces: sensors (foreground process, process list, power status, etc.), the JSON store (settings), registry auto-start, logging, `FolderPetLoader`/`FolderPetCatalog`.
- **App**: the WPF shell. `App.xaml.cs` wires everything up with the Generic Host. `Rendering/` handles the pet frame cache and hot switching (`PetSwitcher`) and decoding of panel preview images (`PetPreviewFrames`). The panel's first tab is "Pets" (`PetsTabViewModel`/`PetCardViewModel`): it lists every pet under `pets/`, and the animated preview only cycles through the states the pet itself defines (Idle first each round, then the rest in random order, no repeats within a round and none twice in a row; `PetShowcase.RandomOrder`). Capability tags are derived from the manifest by `Domain/Pets/PetCapabilities`, with no pet hard-coded. Also in App: `Windows/`, `ViewModels/`, `Interop/` (Win32 interop), `TrayIconService`, `SingleInstanceGuard` (single-instance mutex) and `InstanceSignal` (named events: `DeskBuddy.exe --quit` makes the running instance exit gracefully and waits for it to finish, which the installer uses instead of killing the process; any process other than the tray that sends commands to the running instance goes through it; when the app is launched again, the newly started process signals `DeskBuddy.Activate` so the running instance shows the pet and opens the panel, then exits itself).
- **Error text**: exception messages (mostly English) only go to the log; reasons shown to the user always go through `Presentation/ErrorText.For` (update-related ones through `UpdateErrorText.For`) so they are in the UI language.
- **Visibility**: `Domain/Visibility/PetVisibility` has three independent hide reasons: manual hide by the user, a full-screen program, and session lock (App subscribes to `SystemEvents.SessionSwitch`). While hidden, the pet window stops its animation/walking/pointer timers. When monitors, resolution, scaling or the work area change (`WindowStyleHelper.IsScreenLayoutChange`), the pet window repositions itself.

- **Long-lived states "stroll"**: Coding and the long-lived scenario states (`PetStateExtensions.CanStroll`: Coding / Building / Reading / NightCoding / Meeting / Chatting; Tired, LowBattery and transient states do not count) are pinned by the state machine, so the pet does not move. To avoid hours without motion, `PetBehaviorStateMachine` temporarily enters a normal `Walk` in these states every `StrollIntervalMin..Max` (default 10–20 seconds) (same duration as a normal walk, including the occasional Hop), then returns to the original state; the window layer needs no changes. The switch is the setting `PetSettings.StrollWhileBusy` ("Behavior" tab, on by default), applied to `PetBehaviorOptions.StrollEnabled` via `SettingsApplier`. When adding a new long-lived scenario state, also decide whether it belongs in `CanStroll`.

## Pets

- A pet is a sprite atlas `atlas.png` (all frames laid out as a grid of equally sized cells) plus `manifest.json` under `pets/<name>/`. This is the only format; "one PNG per frame" is no longer supported. Manifest fields: `name`; optional `names` (display names per language, keyed by language such as `zh`, `en` or by region such as `zh-CN`; the panel and tray pick by UI language, falling back to `name`); `frameSize`; required `atlas` (`image` is the atlas file name, `cell` is the cell size in pixels `[width,height]`, optional `columns` is cells per row, defaulting to as many as fit in the atlas width); `states`: each state's `fps` and `frames`, where `frames` are atlas cell indices counted by row from the top-left. `Idle.Left/Right/Up/Down` are the gaze-direction frames. `Glide` may have optional `grips`: one or two points `[x, y]` in `frameSize` units where the pet holds on to the umbrella or parachute (`Pet.GlideGrips`, as `FramePoint` fractions). With two, the parachute strings split between them (left strings to the left point, right strings to the right one, no middle string over the head) and the umbrella shaft goes straight up from the point further right, the canopy centered over it; with one, everything meets there. Without `grips` the pet holds on at `Pet.DefaultGlideGrip` (top middle, 12% down), the old behavior. Grips are mirrored with the frames when the pet faces the other way (`CanopyRig.For`). A real pet cannot reach over its own head, so shipped pets hold on beside the head (paws drawn in front of the head) or, like the ghost with no hands, at the top of the head; every shipped pet that glides defines `grips` (`ShippedPetsTests`), and the generation scripts write them from the same numbers that draw the paws (`Format-GlideGrips` in `PetVectorDrawing.ps1`; `` / `.OverL/OverR` in `PetVectorAnimations.ps1`). `pets/` is copied to the App output directory at build time.
- Frames are still string ids in Domain: `Domain/Pets/FrameId` encodes "atlas path + cell rectangle" as `path#x,y,w,h` (produced by `FolderPetLoader`, which also validates the atlas size and cell indices against the PNG header). `PetFrameCache` / `PetPreviewFrames` share `Rendering/FrameImages`: each atlas is decoded once and then cut into independent copied frames by rectangle (not dragging the whole atlas along). The frames used by panel previews are cut ahead of time on a dedicated STA thread by `PetPreviewFrames.PreloadAsync` (called by `PetsTabViewModel` and `InstalledPets` when loading pets), so the UI thread never decodes atlases. The loader also checks that the atlas cell matches the aspect ratio of `frameSize`. Which image the tray icon uses is decided by the pure function `Presentation/TrayIconModel.Choose`; the tray icon is created only after the pet list has been read, so a default icon is not shown first and then changed.
- A pet folder may contain `icon.png` as the tray icon (head only, filling the image as much as possible; `InstalledPets.IconFileName`). Without it, the tray icon falls back to the upper part of the first Idle frame (`AppIcon.FocusArea`). The pets shipped in the repository get it generated by their own generation scripts (`Save-HdIcon` in `PetVectorDrawing.ps1`, with the head region defined in the script). The generation scripts first draw single-frame PNGs, then `tools/PackPetAtlas.ps1` packs them into `atlas.png` with content de-duplication, replaces the manifest's frame names with cell indices and deletes the single-frame files, so each pet folder contains only `manifest.json`, `atlas.png` and `icon.png`.
- **Every frame must stay inside its cell**: nothing may be cut off at the frame edges (head, ears, tail, props), in every state, including the frames that are tilted, lifted (`-Dy`), rotated (climb), flipped or mirrored (ClimbDown, Ceiling, the right edge). The only content allowed to touch an edge is what is meant to touch it: feet on the ground, the paw or body against the wall in Climb, the feet on the ceiling. When drawing or changing a pet, keep a margin around poses that are later tilted or lifted (a side view whose nose sits at the frame edge gets cut as soon as a hop tilts it), remember that on a wall the "ground" is the screen edge, so a hop lifts the pet away from it (`-Dx`), not up the wall, and check the regenerated atlas frame by frame for opaque pixels on the cell borders before finishing.
- **Manifest limits enforced by `FolderPetLoader`** (a pet that breaks one is rejected with an `InvalidDataException` whose message names the limit; add a test in `FolderPetLoaderTests` whenever a limit is added or changed):
  - `fps` of every state (including `Idle.*` looks) must be between `PetAnimation.MinFps` (0.1) and `PetAnimation.MaxFps` (120); a speed outside it would freeze the UI thread or make the animation timer throw. Every state also needs at least one frame.
  - `atlas.image` must resolve to a file inside the pet's own folder (subfolders are fine); an absolute path or a name that leads out with `..` is refused.
  - `frameSize` may be at most `MaxFrameEdge` (1024) per edge, as it sizes the pet window.
  - The atlas image may have at most `MaxAtlasPixels` pixels (8192 x 8192), because it is decoded whole.
  - The atlas cell must have the proportions of `frameSize`, at least one row of cells must fit in the image, and every frame index must be a cell of the atlas.
  - `Glide.grips`, when present, must have one or two points, each two numbers on the frame (`0..frameSize`, edges included); grips on other states are ignored.
  - Settings reject a pet name that is not a plain folder name (`PetSettings.Normalize`).
  - New limits must be checked against the pets in `pets/` and the generation scripts, and must be written here.
- Pets are looked up in two directories: the user directory `%LOCALAPPDATA%\DeskBuddy\pets` (under the data directory; install/upgrade never touches it) and `pets/` next to the program; on a name clash the user directory wins. `FolderPetCatalog` accepts several roots, and `IPetCatalog.GetPetDirectory(name)` returns a pet's directory; always load pets through it and never build `pets/<name>` yourself. The "Open pet folder" button on the Pets tab opens the user directory.
- The default pet is `robot` (`PetSettings.DefaultPetName`). When a pet cannot be found or fails to load, the app falls back to the default pet. A pet name must be a plain folder name (`PetSettings.Normalize` rejects names containing a path).
- **Throwing the pet**: while dragging, `Domain/Movement/ThrowTracker` records the pointer positions of the last `ThrowSampleWindow` (100 ms); when the release speed exceeds `ThrowMinSpeed` the pet is thrown. The vertical part is handled by `FreeFall` (the initial velocity may point up, and `ceilingY` stops it at the top of the screen); the horizontal part is handled by `ThrowMotion`, which applies air resistance and bounces off both ends. A thrown pet does not grab an edge; a drag that is interrupted (mouse capture lost) counts only as a drop.
- A pet does not have to provide every state: missing states fall back to similar ones through `Domain/Pets/PetStateFallback`. When adding a new `PetState`, also consider the fallback rule and update robot's manifest and `GenerateRobotPet.ps1`. The exception is optional states: `Hop` (a random hop while walking) only happens for pets whose manifest defines it, and a pet without it never enters that state at all (its duration comes from the pet's own `Hop` animation, and the window calls `PetBrain.OnHopEnded` when it finishes playing); robot deliberately has no `Hop`, and `PetCapabilities` does not count it in the total number of states for pets that do not define it.
- `tests/DeskBuddy.Infrastructure.Tests/Pets/ShippedPetsTests` validates the pets shipped in the repository (the repository's `pets/` is copied to the test output directory at build time).

## Themes (dark / light)

- The setting `PetSettings.Theme` (`AppTheme`: follow system / light / dark) is switched on the "Appearance" tab and takes effect immediately; the Windows high-contrast theme takes precedence over this choice.
- **The UI is custom-drawn, styled after ManagedDrive; the WPF Fluent theme is not used** (no `Window.ThemeMode`, no merged `Fluent.*.xaml`). `Themes/AppTheme.xaml` (merged in `App.xaml`) defines all control styles: `Button` (outlined), `TextBox`, `ComboBox`, `CheckBox`, `RadioButton`, `ToolTip`, `ScrollBar`, `ContextMenu` / `MenuItem` / separator are implicit styles, and the rest (`RaisedButton`, `FlatButton`, `IconButton`, `AppTabControl`, `SettingsGroupStyle`, `SettingsCardBorderStyle`, etc.) are used by name. When adding a new control type, add its style here first, otherwise it shows the classic look.
- `App/Presentation/ThemeService` only handles the palette: following `ThemeResolver.Resolve`, it merges `Themes/Colors.{Light,Dark,HighContrast}.xaml` into the application resources (replacing them when the theme changes). All colors are read through `DynamicResource`, so switching takes effect immediately. Color keys use the `App*` prefix (`AppPrimary`, `AppSurface`, `AppDivider`, `AppForeground`, `AppForegroundMuted`, `AppHover`, ...); the three palettes must define the same keys (`ColorFiles_LightDarkAndHighContrast_DefineTheSameKeys` checks this). The high-contrast palette maps every key to `SystemColors`.
- **Normal windows (panel, dialogs)** use `DialogWindowStyle` (borderless + 48px custom title bar + close/minimize buttons; the content margin comes from the window's `Padding`). Rounded corners, border and shadow come from DWM (the attached property `UseNativeCorners` of `Interop/WindowCornerHelper`; on Win10 it falls back to a 1px `AppDivider` border). **Do not use `AllowsTransparency` or draw your own rounded `Border`**, otherwise white edges appear at the four corners. Title bar buttons use `Presentation/WindowCommands`. These windows fetch resources from `AppTheme.xaml` with `DynamicResource` so they can be constructed without an `Application` (in tests).
- **The pet, umbrella and bubble are transparent windows**: do not apply the borderless window style to them. The umbrella window (`Windows/UmbrellaWindow`, laid out by `Presentation/CanopyPlacement`) reaches from the dome above the pet down to the pet's grips and is kept just behind the pet window (`WindowMover.PlaceBehind`), so the paws cover the ends of the shaft and strings. Bubble buttons use their own styles in `Themes/BubbleButton.xaml`, with colors again taken from `App*`.
- User-visible confirmations / questions go through `Presentation/Dialogs.Show` (the custom `DialogWindow`); do not use the system `MessageBox` again. The only exceptions are the two startup-failure / crash spots (theme and host may not be ready then). The tray menu is H.NotifyIcon's WPF `ContextMenu`, styled from `AppTheme.xaml`; the names `PART_Popup` and `SubmenuBorder` in its template are looked up by `TrayIconService.AlignSubmenu` and must not be changed.
- Entrance effects (fade in, pop) all use `Presentation/Motion`, which is skipped automatically when the system turns animations off (`SystemParameters.ClientAreaAnimation`).
- The project no longer needs `NoWarn` for `WPF0001`.

## Settings and process lists

- **The settings page is "draft + save"**: changes on the Appearance / Behavior / System tabs are written only to the draft in `Application/Settings/SettingsEditor` (draft = saved settings + the user's per-field edits). Clicking "Save" applies them through `SettingsService.UpdateAsync`, and "Revert" discards the draft; closing the panel with unsaved changes asks for confirmation. The Pets tab and the tray menu still apply on click. When the saved settings change elsewhere (for example the tray changes the size), fields the user has not touched in the draft follow the change, while touched ones keep the user's value. Invalid input (such as an invalid number of minutes, or a process-list conflict) blocks saving but keeps the typed text; the mutual-exclusion check on process lists runs against the draft. Auto-start (registry) and the boss key (must be registered with the system) are not pure settings: they are applied at save time, rolled back with a message on failure, and the other settings are still saved. Use `Domain/Settings/PetSettingsComparer` to compare settings for changes (a record's built-in equality compares lists by reference).
- Settings are stored in a JSON file (`Infrastructure/Storage/JsonSettingsStore`). **Defaults only apply when there is no config file, on first launch**; once a config file exists, a missing process list (development, meeting, chat, full-screen) or "disabled scenarios" list is treated as empty, never filled with defaults, and new default entries must not be added to them on read. Only a single missing value (a switch, a time, etc.) uses its default. The boss key (`BossKey`) may be empty (unset): `""` in the JSON means the user cleared it, and only a missing field uses the default; an unparsable value falls back to the default.
- Process-name lists follow two rules managed by `Domain/Settings/ProcessListRules`: a process name cannot contain spaces, and a process can be in only one list. The settings page validates input with `Check` (on an error nothing is applied and the reason is shown under the box); on reading the config file and on every settings change `SettingsService` calls `Enforce`, where a duplicate name stays only in the more important list (meeting apps > chat apps > development tools > full-screen programs), the removed names are logged, and a hint appears under "Recognized programs" on the settings page. When adding a process list, also update `ProcessListKind`, the getters/setters/order in `ProcessListRules`, and the settings page.
- When adding a scenario (a situational state in `PetState`), update all of these: `ScenarioCatalog.All` (the list of switches on the settings page) and, where needed, `AmbientRanking`, `ScenarioStates` in `PetCapabilities`, `PetStateFallback`, the `Scenario*` (full sentence, hover tooltip) / `ScenarioName*` (short name shown next to the switch) / `StateHint*` keys in both resx files, and robot's manifest and `GenerateRobotPet.ps1`. Scenarios stay pet-agnostic: a scenario only maps to a `PetState`, and pets opt in by defining that state.
- Number input boxes use `Presentation/DigitsOnly` to accept digits only; times of day (such as the off-work time) are picked with hour and minute drop-downs and cannot be typed.

## Auto-update

- The whole update flow is delegated to the NuGet package `GitHubReleaseUpdater` (`UpdateController` in the `GitHubReleaseUpdater.AutoUpdate` namespace): it looks up the latest **stable** Release of `coldhighsun/DeskBuddy` (pre-releases excluded), picks the `.exe` asset whose name contains `Setup` (`PatternAssetSelector("*Setup*.exe")`; the default selector requires the file name to carry the OS/architecture, which the installer name does not), downloads and verifies it, and launches it with Inno `/SILENT`, after which the app exits. The updater adds `/RELAUNCH=1` to the installer; the `[Run]` entry in the `.iss` uses `Check: ShouldLaunchApp`, so a silent install restarts the app only with that switch, and other silent installs (winget, scripts) do not launch the app.
- Only the App layer has update code: `App/Presentation/AppUpdates.Create` assembles `ReleaseUpdater` and `UpdateController` (it returns null when the version cannot be parsed, in which case the panel's "About" tab (`Windows/AboutView`, the panel's fifth tab, not one of the draft/save settings tabs) hides the update section). `TrayUpdatePresenter` implements `IUpdatePresenter` (tray balloons only; it agrees to `ConfirmInstallAsync` because the user already pressed the button of the update dialog, only logs install failures, and exits the app on `InstallerStarted`). **Offering, downloading and installing happen in `Windows/UpdateDialog`** (opened by `UpdateDialog.ShowFor`, one at a time): version, current version, release notes, a progress bar with size and speed, cancel download, retry after a failure, "skip this version" (`UpdateController.SkipVersionAsync`, remembered in `update-state.json`), "remind me later" and a link to the release page; for a release without an installer it only offers the release page. It is opened by clicking the new-version balloon, by the tray entry "Update to x" and by a manual check on the About tab that finds a version (`AppUpdates` sets `AskToInstallAfterManualCheck = false`, so the controller itself no longer asks). After `InstallAsync` returns, the dialog reads the controller: a `LastFailure` that is not a check failure shows its `UpdateErrorText`; state `Downloaded` means the installer was downloaded but not started (UAC declined) and offers a retry that reuses the file; anything else means the installer started and the app is exiting. What the dialog decides without a window (which controls each state shows, size/progress/failure texts, trimming the notes) lives in `Presentation/UpdateDialogModel` and is unit-tested. The first check runs 30 seconds after startup and then every 24 hours; the setting `AutoCheckUpdates` controls automatic checks via `IsAutoCheckEnabled`. Development builds (`0.0.0-alpha.0.N` given by MinVer when there is no git tag, `AppUpdates.IsDevelopmentBuild`) never check automatically, so a prompt cannot replace the process being developed with a release build; manual checks still work. The "Check for updates" entry is only on the About tab (the tray menu no longer has it; the tray shows "Update to x" only when a new version is found). A manual check ignores the 6-hour throttle (`update-state.json`, written by the package's `JsonFileLastCheckStore`).
- When a new version has no downloadable installer, `HasInstaller` is false: the tray does not show "Update to x" and the About tab shows `UpdateNoInstaller`. `CleanDownloadDirectory` is on, and the download directory (DeskBuddy/update under the temp directory) is used only for updates.
- The release flow uploads two assets: the installer (loose files) and the portable zip (`DeskBuddy-Portable-*.zip`, single-file publish, name without `Setup`, so the updater never picks it). `AppUpdates` explicitly enables `RequireVerifiedDownload`: verification relies on the asset `digest` returned by the GitHub API, and the installer is not launched when it is missing. Exception messages from the package are in English and only go to the log; failure reasons shown to the user always go through `UpdateErrorText.For` (add an entry there for any new exception type).

## Localization

UI text lives in `src/DeskBuddy.App/Resources`: `Strings.resx` is Chinese (the default) and `Strings.en.resx` is English. Add new text to both files (no test checks that the keys match on both sides, so check by hand), and read it in code through the same-named property of `Resources/Strings.cs`.

- **Changing the language (after saving in settings) takes effect immediately, with no restart**: `App.ApplyLanguage` writes the language into `Strings.Culture` (application level). All text and pet display names are read through `Strings.Current`; **do not use `CultureInfo.CurrentUICulture` directly** (the UI thread's own language does not follow `DefaultThreadCurrentUICulture`, and values set in async/dispatcher callbacks get lost); when no language is chosen (in tests), `Current` falls back to the thread language.
- Text in XAML is always written as `{res:Loc KeyName}` (`Resources/Loc.cs`; the key is the name of a `Strings` property, and a wrong key throws when loading). **Do not use `{x:Static res:Strings.X}`**: it reads only once and does not change when the language switches.
- View models that cache text (list item names, card descriptions, etc.) must subscribe to `LocalizedStrings.Instance.LanguageChanged` and rewrite the text (the subscription is a weak reference, but unsubscribe anyway when no longer needed). Text set in code in windows/the tray is refreshed by `App.SwitchLanguage` calling `RefreshLanguage()` on each of them (tray, pet window). Text fixed at generation time, such as errors and notices, does not refresh with the language.
- Pet display names are not in resx: they come from the manifest's `names` (see Pets), so a new pet never needs a resource entry.
